## 3. Decisions for arch-design-system (open items from intake)

- **D1 – AudienceType / audience.ts / builder (FR-3, FR-7, FR-14).** PRD-12 is absent. Recommendation: SH-14 defines `enum AudienceType { SCHOOL GRADE_LEVEL SECTION COURSE }`. `EventAudience` gets `type`, `targetId String?` (null for SCHOOL) and `roles Role[] @default([])`, where empty means all roles. `roles` covers "Grade 7 parents". Resolver in `src/server/audience/audience.ts`, builder in `src/components/AudienceBuilder/`. Both are named generically so PRD-12 adopts them instead of re-creating them. Membership: SCHOOL = all active users; GRADE_LEVEL = students whose current-year SectionMember section has that grade (or `StudentProfile.gradeLevelId`, pick one) plus their parents plus teachers of those sections or courses; SECTION = members + homeroom teacher + parents; COURSE = ACTIVE enrollments + teacher/co-teachers + parents.
- **D2 – FR-20 host page.** No `/admin/academic-years/[id]` UI exists. The minimal option is a small server page at that exact path that lists the year's terms (read-only) with an "Add term breaks" button. Full academic-year CRUD UI is out of scope. Add no nav entry; link to it from the calendar editor or admin, or reach it by URL.
- **D3 – Holidays vs School events chips.** Use intake's default: no duplication. HOLIDAY/TERM_BREAK/`isNoSchool` events appear only under "Holidays".
- **D4 – RSVP guests.** Parents only. The server forces 0 for other roles.
- **D5 – Email default per category (FR-28).** The registry's `defaultEmail` is per type. Options: (a) two types, `event.created` (defaultEmail false) and `event.holiday_created` (defaultEmail true); or (b) one type that passes `email` only for HOLIDAY/TERM_BREAK, which ignores the user preference toggle semantics. Recommend (a), because it stays inside the existing preference model with no changes to notify.ts.
- **D6 – Nav.** Add `/calendar` (all roles). `/account/calendar` gets no sidebar entry, consistent with the existing account pages. It is reached from the account menu and a "Subscribe" link on `/calendar`.
- **D7 – Robotics Club course (FR-37).** Not in the seed. Recommend seeding a minimal ELECTIVE course `ROBOTICS` (teacher Tom, current year) only if absent, so the Chess club example works. The alternative is skip-with-log.
- **D8 – Feed URL display vs hashed storage (FR-24/25, NFR-5).** The raw token is only available at creation or reset. Recommendation: `GET /api/me/calendar-feed` returns `{url}` only when it creates the first token, and `{url:null, createdAt}` otherwise. The page then says "Reset link to get a new URL". This needs to be explicit in the API contracts.
- **D9 – Schema deviations from the PRD's model list** (flag them in system-design): `CalendarEvent.rsvpReminderSentAt`, `EventAudience.roles`, `@@index([type,targetId])`. Each traces to FR-23, FR-3/FR-37 and NFR-4.

## 4. Risks

- **R1 (high):** `@mui/x-scheduler` is beta. Its API (views, timezone, all-day exclusivity, custom event rendering for chips/colours) is unverified until MCP is consulted. Budget for fallbacks (FR-9).
- **R2:** The import cycle between timetable-service and calendar-service (B4).
- **R3:** DST correctness spans four places (FR-15 expansion, FR-4 storage, FR-26 VTIMEZONE, UI). One shared pure helper set in `src/lib/dates.ts` keeps them consistent.
- **R4:** Audience resolution is the performance hot path (NFR-4) and the security boundary (NFR-5/7). It needs a single implementation, tested per role.
